# Evolve — 迭代进化引擎

## 什么时候用

**迭代模式**：用户明确说"迭代一下"、"反复改到满意"、"帮我打磨到满意"。需要用户有明确的迭代意图，"帮我优化"一词单独出现时不触发。

**进化模式**：用户说"进化一下"、"多方向探索"、"从 XX 和 YY 两个方向对比"。不确定最优方向时使用。

### 不要触发的场景
- 简单修改一个函数/SQL/正则 → 直接改
- 用户没有明确说"迭代"、"进化"、"反复" → 不触发
- 数据科学项目优化 → 用 ds-project-optimizer
- 架构改进/重构 → 用 improve-codebase-architecture
- debug/诊断 → 用 diagnose

## 模式

| 模式 | 风格 | 场景 |
|------|------|------|
| `strict` | 逐项检查 | 生产代码 |
| `balanced` | 整体+细节（默认） | 日常开发 |
| `wild` | 鼓励突破 | 原型探索 |
| `evolve` | 多方向竞争 | 开放性问题 |

用户说"像 Linear 那样" → `balanced` 模式 + 在 Review prompt 中加入用户描述作为审美锚点。

## 迭代模式

```
Worker 执行 → Review 独立审查 → 决策 → 循环
```

1. Worker 执行/修改代码
2. Review Agent 审查（通过 Agent 工具创建独立子 agent，不共享上下文）
3. 决策：
   - PASS → 输出最终版本，结束
   - FAIL → Worker 按 Review 的修改建议改，进入下一轮
   - 连续 2 轮无 critical/major 问题 → 问用户"差不多了？"
   - 达到 max_rounds（默认 5）→ 强制结束

## 进化模式

```
生成初始版本 → N 个变异体独立生成 → 独立评估 → 择优 → 循环
```

1. Worker 生成初始版本（第 0 代）
2. 对每个变异角度，用 Agent 工具创建独立子 agent 生成变异体（串行执行，每个变异体独立不共享上下文）
3. 对每个变异体，用 Agent 工具创建独立子 agent 做评估
4. 选择：
   - 淘汰功能正确性 FAIL 的变异体
   - 剩余变异体中，选择总分最高的作为胜出者
   - 如果 Review 认为本代最优相比上一代没有实质性改进（文字判断，非分数比较）→ 收敛，结束
   - 所有变异体均 FAIL → 选择问题最少的作为下一代基线，继续。连续 2 代全部 FAIL → 停止
   - 达到 max_generations（默认 5）→ 强制结束
5. 以胜出者为基线，回到步骤 2（下一代变异）

### 变异角度

| 角度 | 方向 | 评估侧重 |
|------|------|---------|
| `perf` | 性能优化 | 复杂度、IO、缓存 |
| `clarity` | 可读性 | 命名、结构、注释 |
| `wild` | 野路子 | 非常规解法 |

默认 `perf + clarity + wild`。用户可自定义，LLM 根据角度名称推断变异指令，执行前向用户确认。

下一代变异基于上一代得分最高的存活体。多个存活体得分相同时任选一个。

## Prompt 模板

### 变异 prompt

```
你是一个专注于 [{angle_name}] 的代码优化 agent。

变异指令：{angle_instruction}
原始代码：{base_version}

要求：
1. 保持功能正确性不变
2. 从 [{angle_name}] 的角度重新思考和改造
3. 允许大幅重构
4. 只输出被修改的文件的完整内容，未修改的列出路径即可

输出：改造后的代码 + 变异说明（做了什么、为什么）
```

### Review prompt（迭代模式）

```
你是一个 [{mode}] 模式的代码审查 agent。

审查对象：{文件路径和内容}
{如果用户指定了参照物，加入：审美锚点：{用户描述}}

输出格式：
1. 结果：PASS / FAIL（PASS = 可以接受，FAIL = 需要修改）
2. 问题清单（每个标注严重性：critical / major / minor）
3. 具体修改建议（可直接执行的代码）
4. 置信度：HIGH / LOW（HIGH = 确定是问题，LOW = 不确定，可能需要用户判断）
```

### Review prompt（进化模式）

```
你是一个 [{angle_name}] 方向的评估 agent。

评估对象：{variant_content}

输出格式：
1. 功能正确性：PASS / FAIL
2. 角度契合度：无改进 / 有改进 / 明显改进 / 质的飞跃
3. 创新性：常规 / 有巧思 / 非常规且有效
4. 关键发现：最值得保留的一个优点
5. 风险提示
6. 置信度：HIGH / LOW
```

进化模式用定性描述（"明显改进"/"有巧思"）而非数值打分，避免 LLM 评分不稳定导致误判收敛。

## 初始化规则

工作目录：`.evolve/<task-slug>/`

`<task-slug>` 生成规则：取任务描述的关键词，kebab-case，max 30 字符。如"优化排序函数" → `sort-optimize`。

```bash
mkdir -p .evolve/<task-slug>/
cp <source-files> .evolve/<task-slug>/
```

## 成本参考（给用户看，非执行指令）

- 迭代模式：每轮约 2x（Worker + Review），默认 5 轮 = 10x
- 进化模式：每代约 2x × N 个变异体（N 默认 3，即 6x/代），默认 5 代 = 30x
- 进化模式第 1 代开始前告诉用户预计总消耗

## 实战经验

- **两轮迭代是 sweet spot**：第一轮方向性重构，第二轮修 bug，第三轮收益递减
- **给 Worker 的 context 要详细**：逐条列出改什么、输出路径、保持什么不变
- **3 个变异体是 sweet spot**：少于 3 探索不够，多于 3 token 翻倍收益递减
- **进化谱系图比最终代码更有价值**：用户看到"为什么选了这个方案"更能建立信任
- **功能正确性是硬门槛**：有 bug 的变异体必须淘汰
